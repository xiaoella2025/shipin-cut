## 1. 当前稳定状态

| 模块 | 状态 |
|---|---|
| 视频导入 | 稳定 |
| 字幕识别（whisper.cpp 本地） | 稳定 |
| 切片 / 组合方案生成 | 稳定 |
| 剪映草稿导出（atomic，失败不留坏草稿） | 稳定 |
| 方案1/2/3 导出剪映草稿 | 稳定（含 V2 51fps 漂移、concat 时长漂移已修复） |
| 剪映字幕体系（subtitle material，非 text material） | 稳定 |
| 「打开草稿文件夹」「尝试打开剪映」 | 稳定，用户已实测剪映可正常打开 |
| 运行方式 | 开发态：`npm run dev` + 双击 `启动本地导出服务.bat` 启动 `tools/local_export_server.py`（监听 `127.0.0.1:8765`） |

当前用户操作链路（开发态）：
```
npm run dev（前端，Vite 默认端口）
  + 双击 启动本地导出服务.bat（Python 后端，127.0.0.1:8765）
  → 浏览器手动打开前端地址
  → 完成混剪 → 导出剪映草稿 → 打开草稿文件夹 / 尝试打开剪映
```

这条链路对开发者可用，但**不能给普通学员**：要求他们安装 Python、装 Node、敲命令行、自己记端口。这是本阶段要解决的核心问题。

## 2. 产品最终形态（参考 Storybound）

```
学员下载 Setup.exe
  → 双击安装
  → 桌面出现图标
  → 双击图标启动
  → （未来）输入兑换码
  → 直接使用网页式界面完成混剪
  → 点击"打开草稿文件夹" / "尝试打开剪映" 衔接到剪映精修
```

明确边界（产品定位不变）：**本工具不替代剪映**，只负责"剪映前"的混剪自动化，剪映内的精修、贴纸、音乐、字幕样式、最终发布仍交给剪映本体。

## 3. 技术路线对比与推荐

| 维度 | A. Inno Setup + 本地启动器 | B. Electron 桌面壳 | C. Tauri 桌面壳 |
|---|---|---|---|
| 复用现有前端(Vite)/后端(Python) | 直接复用，零改造 | 前端零改造，后端需内嵌进程管理 | 前端零改造，但 Rust 侧调用 Python 子进程需额外封装 |
| 打包体积 | 小（几十 MB + ffmpeg/whisper 资源） | 大（Chromium 内核，普遍 150MB+） | 中（无 Chromium，但仍需打包 Python 运行时） |
| 开发复杂度 | 低，Inno Setup 脚本 + 一个 Python/批处理启动器 | 中高，需要学习 Electron 主进程/渲染进程模型、IPC | 中高，需要 Rust 工具链，团队当前无 Rust 经验 |
| 与 ffmpeg/whisper-cli 外部二进制配合 | 简单，启动器直接用子进程拉起 | 需要在 Electron 主进程里管理子进程生命周期，配置稍复杂 | 类似 Electron，但 Tauri 生态对"大量外部二进制+大模型文件"的最佳实践更少 |
| 自动更新通道成熟度 | 弱，需自建（Inno Setup 本身不带更新） | 强（electron-updater 等成熟方案） | 中（tauri-updater 较新） |
| 与现状的迁移代价 | 几乎为零，复用现有 `npm run build` 产物 + `local_export_server.py` | 需要把现有 Vite 前端嵌入 Electron 渲染进程，重新设计窗口/菜单 | 同上，且需重写部分前后端交互方式 |
| 风险 | 低 | 中（体积/打包稳定性/Windows 上的杀软误报概率上升） | 中高（生态不成熟，团队无先验经验，调试成本不可控） |

### 推荐路线：**方案 A（Inno Setup + 本地启动器）**

理由：
1. **当前阶段目标是"能装、能点、能用"**，不是"做成正式商业桌面软件"。方案 A 用最小改动量达成目标，与"优先稳"的用户偏好直接匹配。
2. 现有前端是纯静态 SPA（`vite build` 产物即可双击打开 / 由轻量 HTTP 服务托管），现有后端是单文件 Python HTTP 服务（`tools/local_export_server.py`），二者都不需要重构即可被一个启动器拉起，没有引入新的运行时模型。
3. Electron/Tauri 的核心价值在于"内置浏览器内核 + 跨平台 + 自动更新生态"，但当前只服务 Windows 学员、且明确"现在不要直接做复杂自动更新"，这些价值在当前阶段都用不上，反而带来包体积、调试面、杀软误报等新增风险。
4. 后续如果产品方向明确要做"类原生桌面应用"（脱离浏览器窗口、系统托盘、深度系统集成），再评估迁移到 Electron 是合理路径——但那是阶段 6 之后的判断，不是现在。

**结论：阶段 1-4 用方案 A 实施；Electron/Tauri 仅作为阶段 6 之后的可选演进方向记录在案，本轮不展开实现细节。**

## 4. 分阶段实施计划

> 阶段编号沿用 `docs/安装版与商业化方案-20260618.md`：**阶段1（打开草稿文件夹/尝试打开剪映）已通过 `3cc32de`/`93745c2`/`d55c8e5` 完成**，下面从阶段2开始细化。

### 阶段 2 前置：安装版目录约定固化

在写启动器代码之前，先把"安装目录 / 运行目录 / 用户数据目录 / 日志目录"的边界定下来（见第6节目录结构），避免阶段2/3来回返工。这一步不是独立阶段，是阶段2开工前的一个必要前置步骤。

**需要新增的文件**（不修改现有稳定代码）：
- `launcher/` 目录（新建，本阶段详细设计见下）
- `packaging/inno/`（新建，阶段3用，本阶段先占位不实现）

**不改动**：`src/`、`tools/export_video.py`、`tools/local_export_server.py` 的业务逻辑本身（阶段2会让启动器去"调用"它们，但不改它们内部代码）。

**验收标准**：目录结构（见第6节）团队/Codex 对齐后不再调整；明确"哪些目录是只读安装资源，哪些目录是用户可写数据"。

### 阶段 2：本地启动器

详细设计见第5节。

**目标**：用户双击桌面图标 → 自动拉起后端 → 自动打开界面 → 不接触命令行。

**需要新增文件**：
- `launcher/launcher.py`（或打包为 `launcher.exe`，见第7节运行时方案）
- `launcher/launcher_config.json`（记录端口、超时等可调参数，非用户可见）

**不改动**：`tools/local_export_server.py` 内部逻辑（启动器只是"调用方"，新增一个程序化拉起的入口，不改它现有的 `if __name__ == "__main__"` 启动行为）。

**验收标准**：见第5节末尾。

**风险点**：
- 路径写死问题（开发态是 `F:\shipin-cut`，安装版必须从 exe 自身位置反推 app root）。
- 重复启动问题（用户手抖多次点击图标）。
- 端口被占用问题（学员电脑上 8765 端口可能被其他程序占用）。

### 阶段 3：Inno Setup 安装包

**目标**：产出 `ShipinCutSetup.exe`，双击安装，桌面+开始菜单出现快捷方式，支持卸载/覆盖安装。

**需要新增文件**：
- `packaging/inno/shipin-cut.iss`（Inno Setup 脚本）
- `packaging/inno/assets/icon.ico`（应用图标）
- `packaging/build_installer.bat`（一键打包脚本：`npm run build` → 收集资源 → 调用 `ISCC.exe` 编译 `.iss`）

**.iss 脚本需要覆盖**：
- `[Setup]`：APP 名称/版本/默认安装目录（`{autopf}\ShipinCut` 或 `{userappdata}\ShipinCut`，见第5节讨论）、卸载支持、覆盖安装时的版本检测。
- `[Files]`：把 `dist/`（前端 build）、`tools/`（后端）、`local-tools/whisper/`（whisper-cli+模型，若体积过大需评估是否随包还是首次启动下载，见第8节风险）、ffmpeg 二进制、`launcher/` 打包结果全部纳入。
- `[Icons]`：桌面快捷方式 + 开始菜单快捷方式，指向 `launcher.exe`。
- `[Run]`：安装完成后可选"立即启动"。

**验收标准**：
- 全新 Windows 环境（无 Python/Node）双击 Setup.exe 安装成功。
- 桌面图标可双击启动并进入可用界面。
- 控制面板"卸载程序"能正常卸载。
- 二次安装（覆盖安装）不报错、不残留旧版本文件冲突。

**风险点**：
- 安装包体积（whisper 模型文件通常几十到几百 MB，ffmpeg 几十 MB，叠加后安装包可能上百 MB～1GB+，需要在阶段3启动前明确是否可接受，或评估"首次启动按需下载大文件"的拆分方案）。
- 杀毒软件/Windows Defender 对未签名 exe 的拦截提示（学员可能因此放弃安装），需要在文档里准备"信任本软件"的引导说明，证书签名属于更后期投入，本阶段不做。

---

### 阶段 4：兑换码入口占位

**目标**：前端出现"输入兑换码"界面，但不接真实后台，纯本地模拟，为阶段5预留字段和交互形状。

**需要新增/改动文件**：
- `src/` 内新增一个独立的"授权检查"轻量组件（**新增文件，不改动现有页面布局/组合方案/字幕识别相关组件**），例如 `src/components/AuthGate.jsx`（命名待 Codex 实施时确认，需与现有组件命名风格一致）。
- 本地模拟逻辑可以直接用 `localStorage` 模拟"已兑换/未兑换"状态，不需要新增后端接口。

**验收标准**：
- 首次打开显示兑换码输入框。
- 输入预设的几个测试码（如 `TEST-VALID` / `TEST-EXPIRED`）能模拟出成功/失败两种状态。
- 不影响阶段1-3已验证通过的导入/字幕识别/导出全流程——授权门禁只是一层前置遮罩，不嵌入业务逻辑内部。

**风险点**：如果在这一步就开始嵌入真实校验逻辑到导出流程里（比如改 `tools/local_export_server.py` 加权限检查），会提前耦合还不存在的真实后台，属于本轮明确不要做的范围（见第8节）。**阶段4必须保持"纯前端模拟、可一键关闭"的形态。**

---

### 阶段 5：真实兑换码后台

**目标**：把阶段4的占位换成真实可用的兑换码系统。详细字段设计见第8节，本阶段不展开实现。

**预计需要新增**：独立的后端服务（与 `tools/local_export_server.py` 解耦，不应合并进同一个本地 Python 服务，因为一个是"本地离线处理"，一个是"需要联网的授权服务"，职责不同）+ 一个简单管理后台。

**验收标准**：略（留到该阶段单独设计时明确）。

**风险点**：涉及真实计费/权限，错误处理不当会直接影响学员能否使用，需要比前面阶段更严格的测试，**本轮不展开**。

---

### 阶段 6：检查更新 / 自动更新

**目标**：版本检查 → 提示新版本 → 下载新 Setup.exe → 引导用户重新安装（覆盖安装）。**本阶段不做"静默自动更新"**，先做"检测+提示+手动触发覆盖安装"，足够支撑当前规模。

**风险点**：真正的自动更新（后台静默下载替换运行中的程序）涉及文件锁定、权限、回滚等复杂问题，是 Electron 生态的强项而 Inno Setup 路线的弱项——如果未来确实需要这个能力，是重新评估方案B/C的触发点，不是现在硬做。

## 5. 阶段 2：本地启动器详细设计

### 5.1 启动流程

```
用户双击桌面图标 ShipinCut.lnk
  → 指向 {安装目录}\launcher\launcher.exe（或 launcher.py，取决于阶段7运行时方案）
  → launcher 启动：
     1. 从自身可执行文件路径反推 APP_ROOT（绝不写死 F:\shipin-cut）
     2. 检查 127.0.0.1:8765 是否已有本工具的服务在监听
        - 已在运行 → 跳过启动步骤，直接打开浏览器/窗口指向已有服务
        - 未运行 → 进入步骤3
     3. 以子进程方式启动后端：
        python(或内置runtime) {APP_ROOT}\backend\tools\local_export_server.py
        - 工作目录设为 {APP_ROOT}\backend
        - 标准输出/错误重定向到 {APP_ROOT}\logs\launcher_<日期>.log
     4. 轮询 127.0.0.1:8765 健康检查接口（若现有后端没有专门的健康检查路由，
        启动器可退化为"轮询端口是否可连接"，不需要现有后端新增接口）
        - 最长等待 N 秒（如15秒），超时则判定启动失败
     5. 启动成功 → 用系统默认浏览器打开前端地址
        （前端 build 产物作为静态文件，由谁来托管见5.4节）
     6. 启动失败 → 弹出中文错误提示框，并指向日志文件路径
```

### 5.2 防止重复启动多个后端实例

- 启动器在拉起子进程前，先做端口探测（TCP connect 127.0.0.1:8765）。
- 额外加一层"启动器自身的单实例锁"（如 Windows 命名 Mutex，或一个 `.lock` 文件 + PID 校验），防止用户连续双击桌面图标在端口探测的间隙内拉起两个子进程的竞态情况。
- 如果检测到端口已被占用但**不是本工具的服务**（被其他无关程序占用），需要给出明确中文提示："8765 端口被其他程序占用，请关闭占用该端口的程序后重试"，而不是静默失败或误连到无关服务。

### 5.3 关闭处理

- 用户关闭启动器窗口（如果启动器本身带一个最小化的状态窗口/托盘图标）时，询问或默认行为：
  - 推荐默认：**关闭启动器窗口不杀死后端**（后端继续在后台运行，用户下次双击图标会检测到已运行并直接复用），原因是导出任务可能正在进行，强行杀掉子进程会中断学员正在跑的导出。
  - 提供一个明确的"退出工具"选项（如托盘图标右键菜单"退出"），这个动作才真正终止后端子进程。
- 这一点需要和"用户心智"对齐：普通学员关浏览器标签页是常见操作，不应等价于"关闭整个软件"。

### 5.4 前端托管方式

现有前端是 `vite build` 产物（纯静态文件，`dist/index.html` + assets）。两种选择：
- **推荐**：由 `tools/local_export_server.py` 顺带托管静态文件（新增一个极简的静态文件路由分支，处理 `GET /` 和资源文件请求），这样只需要一个进程、一个端口，启动器逻辑最简单。
- 备选：启动一个独立的轻量静态服务（如 Python `http.server`）单独起一个端口。会多一个进程，增加"端口又被占用"的故障面，不推荐作为首选。

> 这一步涉及给 `tools/local_export_server.py` **新增**一个静态文件路由分支（新增代码路径，不改动现有的 `/export` `/export-jianying` 等业务路由逻辑），符合"允许改动范围"。

### 5.5 失败提示与日志

- 所有失败必须是中文提示，且不暴露 Python Traceback/JSON 字段名给用户（保持现有"不露出 JSON 技术词"的原则）。
- 日志路径固定为 `{用户数据目录}\logs\launcher_<时间戳>.log`（见第6节目录设计），错误提示框里附带"点击打开日志文件夹"按钮，方便学员截图反馈问题，而不需要他们自己去找路径。

### 5.6 安装路径可移植性

- 启动器内部**禁止**出现任何写死的绝对路径假设（如 `F:\shipin-cut`）。
- 唯一允许的路径来源：`sys.executable` / `__file__`（若是 .py 直接跑）或 Windows API 取当前 exe 路径（若是打包后的 exe），再用相对层级推导 `APP_ROOT`、`backend/`、`frontend/`、`logs/` 等子目录。
- 验收时必须在**非 F 盘、含中文/空格路径的安装目录**下测试一遍（如 `D:\我的工具\shipin cut`），确认不出现路径拼接错误。

### 5.7 验收标准汇总

- [ ] 双击桌面图标，10秒内出现可用界面（首次启动允许稍长，给出"正在启动"提示）。
- [ ] 重复点击桌面图标不会拉起第二个后端进程。
- [ ] 安装到非默认/含空格路径下功能正常。
- [ ] 强制杀掉后端进程后再次点击图标，能正常重新拉起。
- [ ] 8765 端口被占用时给出明确中文提示，不静默失败。
- [ ] 所有异常都写入日志文件，且日志路径在错误提示中可被一键打开。

## 6. 安装包目录结构

```
{安装目录}\ShipinCut\
  launcher\
    launcher.exe              ← 桌面图标指向这里（阶段7决定是否为 PyInstaller 产物）
    launcher_config.json
  app\
    frontend\                 ← npm run build 产物（dist/ 内容原样拷贝）
      index.html
      assets\
    backend\                  ← tools/ 目录原样拷贝（仅运行所需文件，见第7节资源清单）
      local_export_server.py
      export_video.py
      export_with_jianying.py
      jianying_draft\
    runtime\                  ← 见第7节：内置 Python 运行时（若选此路线）或留空（若选方案 PyInstaller exe）
    ffmpeg\
      ffmpeg.exe
      ffprobe.exe
    whisper\
      whisper-cli.exe
      models\
        ggml-xxx.bin
  config\
    app_config.json           ← 安装时生成的只读默认配置（端口、版本号等）
  logs\                       ← 启动器/后端运行日志
  data\
    export_workspace\         ← 对应现有仓库里的 export_workspace/（用户每次导出的中间产物、debug report）
    input-videos\             ← 对应现有 input-videos/，用户素材
    local-output\             ← 对应现有 local-output/
  license\
    LICENSE.txt
    使用说明.txt
```

### 各部分落位说明

1. **前端 build 文件** → `app\frontend\`，由后端静态路由托管（见5.4）。
2. **Python 后端** → `app\backend\`，与当前仓库 `tools/` 目录内容一一对应，不改动其内部代码结构。
3. **ffmpeg** → `app\ffmpeg\`，与现有 `tools/export_video.py` 里 `_find_local_bin` 的查找逻辑天然兼容（该函数已支持"优先找项目内置路径"，具体相对路径需要 Codex 在实施阶段核对一致）。
4. **whisper-cli 和模型** → `app\whisper\`，对应现有 `local-tools/whisper/` 的角色，需要 Codex 核对 `tools/local_export_server.py` 里 `check_whisper()` 的查找路径列表，让安装版路径被正确识别（或在该函数里新增一个候选路径，**只新增不删除**现有候选，保证开发环境不受影响）。
5. **用户上传视频/导出缓存/日志** → `data\` 和 `logs\`，对应现有 `input-videos/`、`export_workspace/`、`local-output/`。**这是用户数据，安装时创建空目录，卸载时默认保留**（除非用户主动选择"同时删除我的数据"）。
6. **用户本地配置** → `config\app_config.json`，存放端口号等非敏感本地设置。
7. **兑换码状态（阶段5之后）** → 预留 `data\license_state.json`（本地缓存的授权状态，真实校验仍以服务端为准，见第7节"避免简单篡改"）。
8. **安装时创建**：`logs\`、`data\export_workspace\`、`data\input-videos\`、`data\local-output\`、`config\`（创建空目录结构，不写入用户数据）。
9. **卸载时可选保留**：`data\`（用户素材+导出历史）、`logs\`（便于事后排查问题）；`app\`、`launcher\`、`config\` 默认随卸载清除。Inno Setup 的卸载流程需要加一个"是否保留我的数据"的确认弹窗。

## 7. 安装包资源清单与运行时方案推荐

### 7.1 需要包含的资源

| 资源 | 来源 | 备注 |
|---|---|---|
| 前端 build 产物 | `npm run build` → `dist/` | 已验证可正常生成（本轮已跑通 `npm run build`） |
| Python 后端代码 | 当前 `tools/` 目录 | 原样收录，不改动业务逻辑 |
| Python 运行环境 | 见7.2方案选择 | — |
| ffmpeg | 现有项目对 ffmpeg 的依赖（`tools/export_video.py` 里 `FFMPEG`/`FFPROBE`） | 需要内置 Windows 版 ffmpeg.exe/ffprobe.exe，避免学员自己安装 |
| whisper-cli + 模型 | 现有 `local-tools/whisper/` 角色 | 模型文件体积较大，需在阶段3评估是否随装包还是首次启动下载（见风险） |
| 剪映草稿导出脚本 | `tools/jianying_draft/` | 原样收录 |
| 默认配置 | 新增 `config/app_config.json` | 端口、日志级别等 |
| 启动器 | `launcher/` | 阶段2产物 |
| 图标 | 新增 `.ico` 资源 | 需要设计一个应用图标，本轮不涉及 |
| 许可证/说明文档 | 新增 | 简要使用说明，引导"打开后看不到界面怎么办""杀毒软件拦截怎么办" |

### 7.2 Python 运行环境方案推荐

| 方案 | 优点 | 缺点 | 是否推荐 |
|---|---|---|---|
| 一、依赖用户本机 Python | 实施最快 | 学员大概率没装 Python，或装的版本/架构不对，直接违背"不让学员碰命令行"的目标 | 不推荐 |
| 二、内置 Python embeddable runtime | 不需要学员安装，体积比完整 Python 安装包小 | 需要手动处理 pip 依赖（当前 `tools/` 下 Python 依赖很轻量，主要是标准库+subprocess调用ffmpeg/whisper，预计无需第三方包，需 Codex 实施时核对 `requirements.txt` 或 import 列表确认） | **推荐** |
| 三、PyInstaller 打包后端为单一 exe | 用户体验最简单（无需任何运行时），杀软误报率通常比"裸 Python 脚本+embeddable runtime"更低一些 | 打包+调试成本略高，且需要对 `subprocess` 调用 ffmpeg/whisper 外部二进制路径做 PyInstaller 专属的路径适配（`sys._MEIPASS` 等） | 备选，若方案二在实测中暴露问题再切换 |

**当前阶段推荐：方案二（内置 Python embeddable runtime）**，理由：
- 现有后端代码零第三方依赖前提下（待 Codex 核对确认），embeddable runtime 几乎是"零额外打包逻辑"，风险最低，最符合"优先稳"。
- PyInstaller 方案体验更顺滑，但调试面更大（资源路径在打包后会变化，需要专门测试），可以作为方案二验证通过后的**优化项**，而不是首发必须项。

### 7.3 体积与下载策略（风险提示，非本轮决策）

whisper 模型文件（即使用较小的 ggml 模型）通常也有数十到上百 MB，叠加 ffmpeg 后安装包可能达到几百 MB 到 1GB+。建议阶段3启动前由用户（产品侧）拍板以下二选一，本轮不代为决定：
- **方案 a**：全部随装包打包，一次性下载完整 Setup.exe（用户体验最简单，但下载慢）。
- **方案 b**：Setup.exe 只含核心程序，首次启动时由启动器检测缺失资源并提示"正在下载语音识别模型..."（包更小，但首次启动需要联网，且要新增下载+校验+断点续传逻辑，复杂度明显上升，不建议第一版做）。

本清单默认按**方案 a**规划阶段3，方案 b 列为阶段3完成后视实际包体积再评估的备选项。

## 8. 兑换码体系后续接口设计（仅设计，不实现）

### 8.1 用户端交互流程

```
打开软件
  → 启动器/前端检查本地授权状态缓存（data\license_state.json）
  → 若缓存显示"未授权"或缓存过期 → 显示兑换码输入框
  → 用户输入兑换码 → 调用服务端校验接口
  → 成功：
      - 写入本地缓存（含到期时间/剩余次数/套餐类型，附带服务端签名防篡改，见8.4）
      - 界面显示：到期时间 / 剩余次数 / 套餐类型
  → 失败：中文提示具体原因（码无效/已用完/已过期/已绑定其他设备）
  → 后续每次"导出剪映草稿"动作前，先做本地+服务端二次校验（见8.3），通过才执行，
    否则提示"额度已用完，请续费"并阻止导出
```

### 8.2 服务端字段设计

| 字段 | 说明 |
|---|---|
| `code` | 兑换码本体（建议格式如 `XXXX-XXXX-XXXX-XXXX`，避免与常见词混淆，避免 0/O、1/I 混淆字符） |
| `package_type` | 套餐类型（如：次数包/包月/包年） |
| `total_quota` | 总额度（次数或天数，依套餐类型而定） |
| `remaining_quota` | 剩余额度 |
| `expire_at` | 到期时间戳 |
| `device_id` | 绑定设备机器码（见8.4） |
| `redeemed_at` | 兑换时间 |
| `status` | 状态（未使用/已激活/已过期/已禁用） |
| `user_note` | 备注（如客服标记） |
| `created_by` | 兑换码生成来源（用于追溯批次） |

### 8.3 导出时的权限检查

- 导出剪映草稿（即调用 `/export-jianying` 的动作）前，新增一道权限闸门：
  - 先查本地缓存的授权状态是否仍在有效期/有剩余额度内。
  - 若本地缓存判断通过，**仍需要定期联网二次确认**（如每24小时或每N次导出做一次在线校验），防止本地缓存被永久离线绕过。
  - 校验通过 → 正常走现有导出流程（不改动导出本身的业务逻辑，只是在调用前加一道门禁）。
  - 校验不通过 → 阻止导出，给出"额度已用完/已过期，请联系xxx续费"提示。

### 8.4 离线处理

- 允许短期离线使用（如7天宽限期），超过宽限期未联网校验则本地判定为"需要重新联网验证"，暂停导出功能但不清空本地数据。
- 本地缓存文件需要服务端签名（如 HMAC 或非对称签名），客户端只校验签名、不能自行伪造"已授权"状态——单纯改本地 JSON 文件数值不应能绕过校验。

### 8.5 机器码生成

- 建议基于稳定的本机硬件标识组合生成（如主板序列号/磁盘卷序列号的哈希），避免使用容易变化的标识（如 IP、MAC 地址在多网卡/虚拟网卡环境下不稳定）。
- 机器码本身不需要暴露给用户，仅在兑换码绑定时上报服务端。

### 8.6 续费码支持

- 续费码本质是"对已存在的 `device_id`/已有套餐做 `remaining_quota`/`expire_at` 的增量更新"，复用同一套 `code` 校验接口，服务端按 `package_type` 区分是"新激活"还是"续费叠加"。

### 8.7 管理后台后续页面（设计层面记录，不实现）

- 兑换码批量生成/导出页面
- 兑换码使用记录查询（按 code / device_id / 时间筛选）
- 套餐配置管理（新增/编辑套餐类型与额度）
- 异常处理页面（手动解绑设备、手动延期、手动禁用码）
- 数据看板（激活数/活跃设备数/到期提醒）

## 11. 风险点汇总

| 风险 | 影响阶段 | 应对方向 |
|---|---|---|
| 安装包体积过大（whisper模型+ffmpeg） | 阶段3 | 产品侧拍板"全量打包"vs"首次按需下载"，本清单默认全量打包 |
| 8765端口被学员电脑上其他程序占用 | 阶段2 | 启动器需明确检测+中文提示，不静默失败 |
| 安装路径写死导致非默认路径下功能异常 | 阶段2 | 启动器路径推导必须基于自身可执行文件位置，验收时测试含空格/非英文路径 |
| 杀毒软件对未签名exe误报 | 阶段3 | 准备引导说明文档，代码签名作为更后期投入 |
| whisper查找路径在安装版下不被现有 `check_whisper()` 识别 | 阶段3 | 只新增候选路径，不删除现有候选，保证开发环境不受影响 |
| 重复点击桌面图标拉起多个后端进程 | 阶段2 | 端口探测+单实例锁双重保险 |
| 兑换码本地缓存被篡改绕过校验 | 阶段5 | 服务端签名校验，客户端不可信 |
| 过早把真实兑换码校验耦合进导出业务代码 | 阶段4 | 阶段4严格保持"纯前端模拟、可一键关闭"，不动 `tools/local_export_server.py` 业务路由 |
